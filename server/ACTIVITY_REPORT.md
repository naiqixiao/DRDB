# Weekly lab activity report

The lab-specific report is disabled by default. Lab managers, PIs and administrators can configure it under Settings → Scheduled Backend Tasks. A blank recipient uses the lab email. When enabled, the backend attempts delivery every Monday at 08:00 America/Toronto for the preceding Monday-to-Monday week. The backend process must be running, and the lab's existing Gmail credentials must work.

Before enabling a lab, use an authenticated lab-leadership session to inspect `GET /api/personnel/activity-report?week_start=YYYY-MM-DD&include_logs=true`, where `week_start` is a Monday in a completed week. This is a read-only preview: it does not send mail. Compare its database counts to known appointments and check that the production database stores appointment times as Toronto wall time. The implementation compares local midnight boundaries against the database column; do not activate until this assumption is confirmed. Verify that both Sunday-named log files covering the reporting week are present and complete. The preview returns aggregates and data-quality counts, not participant records or raw log text.

The report counts distinct schedule IDs from `Appointment Created` and `Appointment Updated` log events by the user's recorded email. Creation credit remains with the creator even if the schedule is later deleted or reassigned. Events lacking a usable schedule ID or a matching active member are reported in the unattributed count. E1/E2 counts use current assignments and confirmed appointment status at the scheduled time, not a verified completion event; later edits may change a past report. The active roster is the current Personnel population, not a historical roster. These categories can overlap.

The elapsed estimate uses each user's successful `Log in` and the last recognized manual family, child, appointment, study, experimenter-assignment or conversation action before the next login. Automatic events are excluded. Intervals are clipped to the reporting week; ambiguous ordering, missing completion, and unidentifiable logins are excluded. The log stores only local minute precision and has no offset. If a relevant timestamp is invalid or falls in the repeated daylight-saving hour, the estimates are unavailable rather than zero. Estimates are elapsed time between recorded events, not verified active time. They can include idle time and omit work outside DRDB.

The log writer creates a file only when it records an event, so an absent expected file is treated as an error, not proof of zero activity. An incomplete or inaccessible log prevents schedule counts and triggers a failure notification; an estimate calculation failure alone produces blank estimate cells while retaining count data. Failure notifications require working lab Gmail credentials and an available recipient. If those are unavailable, the backend logs an error; email cannot independently report failure of its own transport.

The sender uses a durable per-lab, per-week database claim before sending. Once claimed, a retry does not send again, including after an uncertain Gmail result. Inspect the lab Sent mailbox and the `WeeklyActivitySent_<lab-id>_<week-start>` SystemSetting value before any manual recovery. Never clear a claim and retry without resolving whether the message was sent. Restarting the backend or changing settings does not re-send an already claimed week. No raw logs or participant-identifying data are included in the email or CSV.
